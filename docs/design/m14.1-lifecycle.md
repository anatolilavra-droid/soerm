# M14.1: жизненный цикл findings (design)

Статус: решения утверждены (включая Q1-Q11, раздел 15). Production-код, миграции, тесты,
CLI, TUI и отчёты на этапе design не меняются; реализация - отдельной командой.

## 1. Scope и цели

Повторные сканы должны управлять **состоянием обнаружения** finding, а решения аналитика
оставаться за человеком. Цели:

- учитывать отсутствие finding только в полных сканах той же области;
- закрывать исправленные findings только после верификации повторным сканом;
- повторно открывать findings, вернувшиеся после исправления;
- хранить историю переходов и считать метрики: time to triage, time to remediation, MTTR,
  SLA compliance, reopened rate, false-positive rate;
- не менять решения аналитика автоматически.

Закрытие без повторной проверки не считается доказанным исправлением: повторный полный скан
области - обязательная верификация remediation.

## 3. Термины и модель состояний

### 3.1 Две независимые оси

1. **Статус (решение человека)** - существующий `FindingStatus`. Меняется аналитиком, кроме
   двух явно описанных автоматических переходов: auto-close (`resolved` -> closed) и
   auto-reopen (`resolved` / closed -> `open`).
2. **detection_state (что показывают полные сканы)** - новое поле:
   - `present` - finding найден в последнем полном скане хотя бы одной своей области или ещё
     не проверялся полным сканом;
   - `missing` - отсутствует в полных сканах всех своих областей, но порог закрытия не
     достигнут;
   - `close_candidate` - отсутствует в `close_after_clean_scans` полных сканах каждой своей
     области и grace period истёк.

### 3.2 Представление closed (вариант A)

`closed` не добавляется в `FindingStatus` и в CHECK таблицы `findings`. Закрытый finding:

```
findings.status = 'resolved' AND finding_lifecycle.closed_at IS NOT NULL
```

| Видимое состояние | Хранение |
| --- | --- |
| open / triaged / in_progress | `status` как сейчас |
| resolved (исправление заявлено, не проверено) | `status = 'resolved'`, `closed_at IS NULL` |
| closed (исправление подтверждено сканом) | `status = 'resolved'`, `closed_at IS NOT NULL` |
| accepted_risk / false_positive | `status` как сейчас, только через approval |

CLI, TUI и отчёт показывают `closed` как производное значение.

**Почему вариант A.** CHECK у `STRICT`-таблицы в SQLite нельзя изменить через `ALTER TABLE`;
нужна пересборка `findings` (новая таблица, копирование, `DROP`, `RENAME`). На `findings`
ссылаются `finding_occurrences`, `tasks`, `incident_links` и `pending_changes`; пересборка
требует `PRAGMA foreign_keys = OFF`, а эта PRAGMA внутри транзакции не действует. Текущий
движок выполняет каждую миграцию внутри `BEGIN IMMEDIATE`, поэтому вариант B потребовал бы
изменить сам движок миграций и пересоздать индексы `findings_asset_id`, `findings_status`. Это
самый рискованный вид изменения схемы. Вариант A только добавляет объекты, не трогает
применённые миграции, `FindingStatus`, approvals (`GATED_STATUSES`), `ACTIVE_STATUSES` и
`finding.digest()`.

### 3.3 Область скана (scope)

```
scope_key = sha256(canonical_json({scheme: "soerm-scope-v1", asset_id, tool, profile}))
```

- `asset_id` - актив импорта (`--asset-id`, уже обязателен);
- `tool` - slug инструмента, задаётся явно (`--tool`);
- `profile` - необязательная метка профиля / области (`--scope-label`), по умолчанию `null`.

`tool` и `profile` - строчные ASCII-slug `[a-z][a-z0-9_-]{0,47}`; свободного текста нет.
Finding **принадлежит** области, если хотя бы одна его occurrence получена импортом этой
области (с `--tool`). Отсутствие finding учитывается только в его областях.

### 3.4 Чистый скан

Полный скан области S - **чистый для finding F**, если F принадлежит S и F нет среди записей
этого скана. Скан засчитывается только при выполнении всех условий:

1. импорт с `--complete`;
2. пара `(scope_key, file_sha256)` для S ещё не встречалась;
3. `scanned_at` скана строго больше `last_complete_scan_at` области S.

## 4. Правила обработки импортов

Существующий поток M6 сохраняется. Lifecycle-шаг выполняется **в той же write-транзакции**
после записи findings и occurrences.

| # | Ситуация | Поведение |
| --- | --- | --- |
| I1 | Импорт без `--complete` (частичный) | как сейчас: создание / `last_seen` / occurrence. Если указан `--tool` - запись членства в области. Отсутствие не учитывается; `consecutive_clean_scans`, `missing_since`, `detection_state` к закрытию не продвигаются; ничего не закрывается. Повторное обнаружение (переходы L4 / L5) применяется, если скан не устаревший |
| I2 | `--complete` без `--tool` или без `--scanned-at` | ошибка использования (`scope_tool_required` / `scanned_at_required`, код 2), ничего не пишется |
| I3 | Повтор файла с тем же SHA-256 в той же области | не считается новым чистым сканом; lifecycle не меняется; результат `unchanged` по lifecycle (решение 5). Путь к файлу на это не влияет |
| I4 | Скан старше последнего полного скана области (`scanned_at <= last_complete_scan_at`) | occurrences и `first_seen` / `last_seen` пишутся как сейчас; lifecycle не меняется (решение 6); результат помечается `stale_scan` |
| I5 | Полный скан с новым SHA-256 и более поздним `scanned_at` | для каждого finding области - переходы раздела 5; run создаётся **даже если записей нет или все записи `unchanged`** |
| I6 | В полном скане есть отклонённые записи (`missing_severity`, `invalid_record` и др.) | скан **не считается чистым** ни для одного finding области (`clean = 0`, код `incomplete_scan`); L6-L8 не выполняются; присутствие принятых записей (L2-L5) применяется |

**Правило I5 (пустой полный скан).** Полный скан без записей - не «ничего не изменилось», а
доказательство отсутствия findings в указанной области. Поэтому при `--complete` run, строка
`import_run_scopes` и audit `import.run` создаются всегда, когда пара `(scope_key,
file_sha256)` новая и скан не устаревший, - в том числе при нуле записей и когда все записи
`unchanged`. Это осознанное отличие от поведения M6 для частичных импортов (там пустой файл
по-прежнему даёт `unchanged` без run). Пустой скан с отклонёнными записями подпадает под I6.

**Правило I6 (отклонённые записи).** Отклонённая запись не доказывает ни присутствия, ни
отсутствия: она могла описывать любой finding области. Полный скан с хотя бы одной
отклонённой записью записывается (run, `import_run_scopes` с `clean = 0`), но не
увеличивает `consecutive_clean_scans`, не ставит `missing_since` и не может привести к
`close_candidate` или закрытию. `--default-severity` уменьшает число отклонений
`missing_severity` и остаётся решением пользователя.

**`scanned_at` (Q2).** Для полного скана `--scanned-at TS` обязателен: UTC, не позже текущего
момента, иначе `invalid_input`. Порядок полных сканов определяется только `scanned_at`, а не
временем импорта. Для частичного импорта `--scanned-at` необязателен; без него используется
`imported_at`, и такое значение служит только для проверки устаревания (I4).

## 5. Переходы

Обозначения: `S` - область полного скана; `N = close_after_clean_scans`; `G =
grace_period_hours`. Все переходы, кроме L9-L11, выполняются только внутри импорта под
workspace lock и в одной транзакции с ним. Ни один переход не меняет `owner`, `title`,
`description`, `evidence`, `technical_severity`, `business_priority`, решения approvals.

| # | Предусловия | Изменение состояния | Событие `finding_events` | Audit | Запрет автоизменения |
| --- | --- | --- | --- | --- | --- |
| L1 | Новый fingerprint (любой импорт) | finding `open` (как сейчас); `finding_lifecycle`: `present`; членство в S, если есть `--tool` | `detected` | `finding.create` (существующее) | - |
| L2 | F в полном скане S; статус `open` / `triaged` / `in_progress` | `consecutive_clean_scans(F,S) = 0`; `missing_since = NULL`; `detection_state = present` | `redetected`, только если состояние было `missing` / `close_candidate` | покрыто `lifecycle.apply` | статус не меняется |
| L3 | F в полном скане S; статус `accepted_risk` / `false_positive` | как L2 | как L2 | покрыто `lifecycle.apply` | **статус не меняется никогда** (решение 2) |
| L4 | F найден (полный или частичный, не устаревший скан); статус `resolved`, `closed_at IS NULL`; `auto_reopen = true` | `status = open`; `reopen_count += 1`; `resolved_at = NULL`; `detection_state = present`; счётчики S обнулены | `reopened` (from `resolved`) | `finding.reopen` (before/after hash finding) | исправление не подтверждено - автоматический возврат разрешён политикой; при `auto_reopen = false` только событие `redetected_after_resolve` |
| L5 | То же, но `closed_at IS NOT NULL` (closed) | `status = open`; `closed_at = NULL`; `verification_method = NULL`; `reopen_count += 1` | `reopened` (from closed) | `finding.reopen` | как L4 |
| L6 | F принадлежит S, отсутствует в чистом полном скане S | `consecutive_clean_scans(F,S) += 1`; `missing_since` ставится, если пусто; `detection_state = missing` | `missing`, только при смене состояния | покрыто `lifecycle.apply` | статус не меняется |
| L7 | После L6: для **каждой** области F `consecutive_clean_scans >= N` и `scanned_at - missing_since >= G` | `detection_state = close_candidate` | `close_candidate` | покрыто `lifecycle.apply` | для `open` / `triaged` / `in_progress` / `accepted_risk` / `false_positive` статус не меняется (решения 2, 7) |
| L8 | L7 выполнено; статус `resolved`, `closed_at IS NULL`; `auto_close = resolved_only`; `require_manual_verification = false` | `closed_at = scanned_at`; `verification_method = scan`; `verified_by_run = RUN` | `closed` (method `scan`) | `finding.close` | только из `resolved` (решение 7) |
| L9 | Ручное: `finding verify`; статус `resolved`, `closed_at IS NULL`, `detection_state = close_candidate` | `closed_at = now`; `verification_method = manual` | `closed` (method `manual`) | `finding.verify` | без `close_candidate` отказ `not_close_candidate`: без повторного скана закрытие невозможно |
| L10 | Ручное: `finding update --status resolved` (существующая команда) | как сейчас; `finding_lifecycle.resolved_at = now` | `resolved` | `finding.update` (существующее) | если `close_candidate` уже достигнут, закрытие произойдёт только при следующем чистом полном скане (L8) или через `finding verify` (L9) |
| L11 | Ручное: `finding update` уводит статус из `resolved` (включая closed) | как сейчас; `closed_at = NULL`, `resolved_at = NULL`; `reopen_count += 1` | `reopened` (method `manual`, Q5) | `finding.update` (существующее) | - |
| L12 | Ручное: `finding update` меняет статус между `open` / `triaged` / `in_progress` | как сейчас; при первом входе в `triaged` - `triaged_at`, в `in_progress` - `remediation_started_at` | `status_changed` | `finding.update` | - |

Gated-переходы в / из `accepted_risk` и `false_positive` остаются только через approval (M8);
lifecycle их не инициирует.

## 6. Политика закрытия

```yaml
lifecycle:                          # новая необязательная секция soerm.yaml
  close_after_clean_scans: 2        # 1..10
  grace_period_hours: 0             # 0..8760, отсчёт от missing_since
  auto_close: resolved_only         # off | resolved_only
  require_manual_verification: false
  auto_reopen: true
```

- `auto_close: off` - L8 не выполняется; закрытие только через L9.
- `require_manual_verification: true` - L8 не выполняется; L9 обязателен.
- Монотонность проверяется при загрузке: значения вне диапазона, bool вместо числа и
  неизвестные поля отклоняются (как остальные секции `SoermConfig`).
- Хеш политики (решение 9):

```
lifecycle_config_hash = compute_config_hash(
    name="lifecycle", version="lifecycle-v1", payload=policy.canonical_dict())
```

  Хеш записывается в каждую строку `import_run_scopes` и в события `closed` / `reopened`;
  `soerm config validate` печатает его рядом с `risk_config_hash`. Изменение `soerm.yaml` не
  пересчитывает уже записанные события.

## 7. Reopen semantics

- reopened - **событие** `reopened` в `finding_events` и счётчик
  `finding_lifecycle.reopen_count`, а не статус (решение 8). После повторного открытия статус
  `open`.
- Автоматический reopen (L4, L5) выполняется при повторном обнаружении в неустаревшем скане,
  только из `resolved` и closed, только при `auto_reopen = true`, с аудитом `finding.reopen`.
- `accepted_risk` и `false_positive` никогда не открываются автоматически (решение 2):
  повторное обнаружение для них ожидаемо.
- Изменение статуса меняет `finding.digest()`, поэтому ожидающие approvals на этот finding
  устаревают (`approval_stale_target`) - это желаемое поведение M8.
- Скан с `scanned_at <= last_complete_scan_at` области (I4) не открывает finding: он описывает
  прошлое.

## 8. Схема миграции v3

v3 - **только добавляющая**; v1 и v2 не меняются (их checksum хранится в `schema_version`).
Все statements - литеральный SQL, без построения на лету. Порядок внутри одной транзакции
`BEGIN IMMEDIATE`:

1. `CREATE TABLE` (таблицы в порядке зависимостей внешних ключей);
2. `CREATE INDEX`;
3. `CREATE TRIGGER`;
4. backfill `INSERT ... SELECT`.

Никаких `ALTER TABLE`, `DROP`, `PRAGMA foreign_keys`, изменения существующих индексов и
триггеров. Ошибка любого statement откатывает всю v3 (поведение движка).

| Объект | Тип | Назначение |
| --- | --- | --- |
| `import_run_scopes` | таблица `STRICT` | `run_id` PK -> `import_runs`; `asset_id` -> `assets`; `tool`, `profile` (slug / NULL); `scope_key`; `file_sha256` (копия из `import_runs`, Q10); `complete` (0/1); `scanned_at`; `stale` (0/1); `clean` (0/1, I6); `lifecycle_config_hash` |
| `import_run_scopes_scope` | индекс | `(scope_key, scanned_at)` |
| `import_run_scopes_sha` | уникальный частичный индекс | `(scope_key, file_sha256) WHERE complete = 1` (I3) |
| `finding_scopes` | таблица `STRICT` | PK `(finding_id, scope_key)`; `asset_id`, `tool`, `profile`; `consecutive_clean_scans`; `missing_since`; `last_complete_scan_at`; `last_run_id` |
| `finding_lifecycle` | таблица `STRICT` | PK `finding_id` -> `findings`; `detection_state` CHECK (`present`, `missing`, `close_candidate`); `triaged_at`, `remediation_started_at`, `resolved_at`, `closed_at`; `verification_method` CHECK (`scan`, `manual`) / NULL; `verified_by_run` / NULL; `reopen_count >= 0`; `history_complete` (0/1); CHECK `closed_at IS NULL OR verification_method IS NOT NULL` |
| `finding_events` | таблица `STRICT` | `event_id`; `finding_id`; `occurred_at`; `event_type` CHECK (список событий раздела 5); `from_status`, `to_status` (CHECK по `FindingStatus`, NULL допустим); `run_id` / NULL; `actor`; `method` / NULL; `lifecycle_config_hash` / NULL. Текста нет |
| `finding_events_finding` | индекс | `(finding_id, event_id)` |
| `finding_events_no_update`, `finding_events_no_delete` | триггеры | append-only (как таблицы playbooks в v2) |
| backfill | `INSERT INTO finding_lifecycle ... SELECT FROM findings` | одна строка на каждый существующий finding: `detection_state = 'present'`, `reopen_count = 0`, `history_complete = 0`; `resolved_at` / `closed_at` = NULL |

Инварианты, проверяемые в сервисе (не триггером): `closed_at IS NOT NULL` только при
`findings.status = 'resolved'`; каждая строка `findings` имеет строку `finding_lifecycle`
(новые findings получают её в той же транзакции). Почему не триггером на `findings`: см. Q9.

Совместимость объектов схемы SQLite: новые таблицы, индексы и триггеры не ссылаются на
`sqlite_master` и не изменяют существующие объекты; триггеры v1/v2 (`audit_log_*`,
`playbook_*`) и индексы `findings_*` остаются как есть.

## 9. Audit-события

Новые действия (формат существующего CHECK `audit_log.action`):

| Action | object_type / object_id | before_hash / after_hash | Когда |
| --- | --- | --- | --- |
| `finding.close` | `finding` / `FND-...` | digest finding до / после + хеш строки lifecycle | L8 |
| `finding.verify` | `finding` / `FND-...` | то же | L9 |
| `finding.reopen` | `finding` / `FND-...` | digest finding до / после | L4, L5 |
| `lifecycle.apply` | `import_run` / `RUN-...` | NULL / хеш канонического списка `(finding_id, event_type)` всех событий этого run | один раз на полный скан, если события есть |

- Переходы detection_state (L2, L3, L6, L7) отдельных audit-записей не получают: на 50 000
  findings это 50 000 записей на скан. Их связывает с цепочкой хеш в `lifecycle.apply`.
- Actor автоматических переходов - `--actor` импорта.
- Существующие действия (`import.run`, `finding.create`, `finding.update`) не меняются.
- Audit по-прежнему содержит только идентификаторы и хеши.

## 10. CLI-контракт

Изменения (существующие аргументы и коды выхода не меняются):

```
soerm import run PATH --format ... --asset-id AST-NNNNNN --workspace DIR --actor NAME
                 [--tool SLUG] [--scope-label SLUG] [--complete] [--scanned-at TS] [--json]
soerm finding show FND-...       # + detection_state, closed (производное), reopen_count
soerm finding list [--detection-state present|missing|close_candidate] [--closed]
soerm finding lifecycle FND-... --workspace DIR [--json]          # история событий, read-only
soerm finding candidates --workspace DIR [--json]                 # close_candidate, read-only
soerm finding verify FND-... --workspace DIR --actor NAME --expect-hash H [--json]   # L9
soerm config validate            # + lifecycle_config_hash
```

- `--complete` требует `--tool` и `--scanned-at` (иначе `usage_error`, код 2; Q1, Q2).
- `--scanned-at` - UTC, не позже текущего момента; иначе `invalid_input`.
- `--tool` без `--complete` записывает только членство в области (I1).
- Результат `import run` (`--json`) получает блок `lifecycle`: `scope_key`, `complete`,
  `stale`, `clean`, счётчики `redetected`, `missing`, `close_candidate`, `closed`,
  `reopened`. Без заголовков, путей и значений.
- Новые коды ошибок: `scope_tool_required`, `not_close_candidate`, `status_not_resolved`,
  `already_closed`.
- Чтение (`lifecycle`, `candidates`) не берёт lock и не создаёт БД.
- TUI (только чтение): колонки `detection`, `reopen`, производное `closed` на экране Findings,
  карточка метрик на Dashboard; данные только через сервисы.

## 11. Метрики

| Метрика | Определение |
| --- | --- |
| Time to triage | `triaged_at - first_seen` |
| Time to remediation | `closed_at - first_seen` (только closed, т. е. подтверждённые сканом) |
| MTTR | медиана и среднее time to remediation за период отчёта |
| SLA compliance | доля closed с `closed_at <= sla_due_at` среди closed с `sla_due_at` |
| Reopened rate | доля findings с `reopen_count > 0` среди когда-либо resolved |
| False-positive rate | доля `false_positive` среди findings, прошедших triage |

- Findings с `history_complete = 0` (созданные до v3) исключаются из временных метрик и
  считаются отдельно (`insufficient_history`); даты не придумываются.
- Метрики детерминированы при фиксированном `--generated-at`.
- Отчёт получает раздел `lifecycle`; схема отчёта становится `soerm-report-v2`.

## 12. Backward compatibility

- Схема: БД v2 мигрирует до v3 **первой командой записи** (как v1 -> v2). До этого команды
  чтения, отчёт и TUI отвечают `schema_not_current` (код 3) - существующее поведение.
- Приложение M13 на БД v3: запись - `database_newer_than_application`, чтение -
  `schema_not_current`. Downgrade не поддерживается; в README - рекомендация backup до
  обновления.
- `soerm.yaml` без секции `lifecycle` - значения по умолчанию из раздела 6. Файл с секцией
  `lifecycle` приложение M13 отклонит (неизвестное поле) - ожидаемо.
- Импорт без новых флагов ведёт себя как в M13, кроме записи lifecycle-строки для новых
  findings и автоматического reopen (L4, L5) для findings в `resolved`. Для существующих
  findings без областей reopen возможен только после импорта с `--tool` (членство).
- `ACTIVE_STATUSES`, `GATED_STATUSES`, `finding.digest()` и fingerprint не меняются.
- Пустой файл при частичном импорте по-прежнему даёт `unchanged` без run; новое поведение
  (I5) только для `--complete`.

### 12.1 Переход маркера отчёта v1 -> v2 (Q6)

- Новые отчёты пишутся со схемой `soerm-report-v2` (раздел `lifecycle`); остальные разделы
  и порядок полей v1 сохраняются.
- `outputs/safe_write.py` сейчас признаёт файл «прежним отчётом» по одному маркеру
  `REPORT_SCHEMA` в первых 4096 байтах. После перехода `--force` должен признавать **оба**
  маркера: `soerm-report-v1` и `soerm-report-v2`. Иначе ранее созданный отчёт v1 нельзя
  перезаписать, и пользователь получит отказ на собственном файле.
- Набор признаваемых маркеров - закрытый список констант; файл без любого из них
  по-прежнему не перезаписывается (защита M10 сохраняется).
- Потребители JSON-отчёта различают версии по полю схемы; v1 больше не генерируется.

### 12.2 Ограничения

- Downgrade схемы и приложения не поддерживается: перед обновлением нужен backup (`soerm.db`
  и `soerm.yaml`, как описано в README, раздел M12).
- Findings, созданные до v3, не имеют истории (`history_complete = 0`): их временные метрики
  не считаются, даты не восстанавливаются.
- Существующие findings не принадлежат ни одной области, пока их не найдёт импорт с
  `--tool`; до этого они не могут стать `close_candidate` или closed.
- Findings без областей (`source = manual` или только частичные импорты) остаются в
  `resolved` и не закрываются (Q4).
- Корректность закрытия зависит от честности `--complete`, `--tool` и `--scanned-at`: это
  заявления пользователя, фиксируемые в `import_run_scopes` и audit, а не проверяемые факты.
- Область нельзя переименовать или вывести из эксплуатации (Q8).
- История событий не показывается в TUI (Q11).

## 13. Безопасность и redaction

- `--tool` и `--scope-label` - ASCII-slug с allowlist: секрет в них не помещается как
  свободный текст; значения не печатаются в ошибках.
- `finding_events`, `finding_scopes`, `finding_lifecycle`, `import_run_scopes` не содержат
  текста finding (title, description, evidence), путей и значений из файла.
- Весь lifecycle-шаг идёт в write-транзакции импорта под workspace lock: частичное
  применение невозможно, ошибка откатывает импорт целиком (поведение M6).
- Новых сетевых, процессных и файловых операций нет; слои: `domain/lifecycle.py` (чистые
  функции переходов), `storage/` (репозитории), `services/` (оркестрация), `cli/`, `tui/`
  (через сервисы). `test_layering.py` и `test_tui_policy.py` должны остаться зелёными без
  расширения allowlist.
- Ограничение: автоматический reopen и close зависят от честности `--complete` и `--tool`;
  пользователь, пометивший частичный скан как полный, закроет findings. Это решение человека
  (как `--actor`), фиксируется в `import_run_scopes` и audit.

## 14. План тестирования

Domain (чистые функции переходов):
- таблица переходов L1-L12 для каждой пары (статус, событие скана);
- `accepted_risk` / `false_positive` не меняются ни при каком событии;
- auto-close только из `resolved`; для `open` / `triaged` / `in_progress` - только
  `close_candidate`;
- `close_after_clean_scans` 1..N, `grace_period_hours` 0 и > 0;
- `auto_close: off`, `require_manual_verification: true`, `auto_reopen: false`;
- хеш политики детерминирован и меняется при любом изменении.

Storage / migration:
- v3 применяется на БД v2 из фикстуры; backfill даёт строку на каждый finding;
- checksum v1 / v2 не изменились; повторный запуск ничего не делает;
- триггеры `finding_events` запрещают UPDATE / DELETE;
- откат v3 при ошибке statement.

Services / CLI:
- частичный импорт ничего не закрывает и не продвигает к закрытию (решение 3);
- повтор файла с тем же SHA-256 не считается чистым сканом (решение 5);
- старый скан после нового не откатывает lifecycle (решение 6);
- `--complete` без `--tool` или без `--scanned-at` - код 2, ничего не записано;
- пустой полный скан создаёт run и считается чистым (I5); пустой частичный импорт - `unchanged`;
- полный скан с отклонёнными записями записан с `clean = 0` и не продвигает к закрытию (I6);
- ручной уход из `resolved` увеличивает `reopen_count` (Q5);
- чужая область (другой tool, profile или asset) не влияет;
- finding в двух областях закрывается только при чистоте обеих;
- reopen создаёт событие, `reopen_count` и audit `finding.reopen`;
- `finding verify` без `close_candidate` отказывает;
- approval на finding устаревает после auto-reopen;
- секреты не попадают в новые таблицы, audit и вывод (как e2e M11);
- `config validate` печатает `lifecycle_config_hash`.

Report / TUI:
- метрики на фиксированном наборе; `insufficient_history` для findings до v3;
- отчёт v2 детерминирован; `--force` перезаписывает отчёты v1 и v2 и отказывает файлу без
  маркера;
- TUI показывает новые колонки только через сервисы; policy-тесты зелёные.

E2E: импорт -> `resolved` -> два чистых полных скана -> closed -> finding вернулся -> reopen
-> метрики в отчёте.

## 15. Открытые вопросы

Все вопросы M14.1 закрыты решениями владельца проекта; новых открытых вопросов нет.

| # | Вопрос | Решение |
| --- | --- | --- |
| Q1 | Идентичность инструмента: явный `--tool` или `tool.driver.name` из SARIF. В одном SARIF может быть несколько `runs` с разными driver | **обязательный явный `--tool`** для полного скана; driver name SARIF для scope в M14.1 не используется |
| Q2 | Источник `scanned_at`: в SARIF нет времени результата; `imported_at` неверно упорядочивает старый файл, импортированный позже | **`--scanned-at` обязателен для полного скана**; для частичного импорта необязателен (по умолчанию `imported_at`) |
| Q3 | Reopen из `resolved` (L4), если finding ещё виден после пометки `resolved` | **reopen из `resolved` разрешён** (при `auto_reopen = true`) |
| Q4 | Findings без областей (`source = manual`, только частичные импорты) никогда не станут closed | остаются `resolved`; ручная аттестация без скана - не в M14.1 |
| Q5 | Считать ли ручной уход из `resolved` (L11) reopen | **да**: событие `reopened` с `method = manual`, `reopen_count += 1`, учитывается в reopened rate |
| Q6 | Маркер отчёта для `--force`: v1 и v2 | признавать оба маркера (раздел 12.1) |
| Q7 | Агрегация по нескольким областям | finding становится `close_candidate` только когда **все** его области чистые |
| Q8 | Переименование / вывод области из эксплуатации | вне M14.1; findings остаются в последнем состоянии |
| Q9 | Инвариант `closed_at` только при `resolved` - сервисом или триггером на `findings` | сервисом (триггер на `findings` изменил бы набор объектов v1); проверка в тестах |
| Q10 | Уникальность `(scope_key, file_sha256)` | `file_sha256` дублируется в `import_run_scopes`; уникальный частичный индекс `WHERE complete = 1` |
| Q11 | Ограничение TUI 2000 строк для истории событий | история событий только в CLI `finding lifecycle`; TUI показывает `detection`, `reopen_count`, closed |

## 16. Out of scope

- Настоящий статус `closed` в `FindingStatus` и пересборка `findings` (вариант B).
- Автоматическое изменение `accepted_risk` / `false_positive`.
- Автоматическое определение полноты скана и инструмента.
- Подписи действий и якорение audit (M14.2).
- Новые импортёры, CVE / CWE и дедупликация между инструментами (M14.3).
- KEV / EPSS и новая формула риска (M14.4).
- Export CSV / HTML / PDF, backup (M14.5).
- Изменение SLA-модели (`sla_due_at` от `first_seen`) и fingerprint.
