# SOERM Roadmap

## Позиционирование

SOERM - приватная offline-first платформа управления findings для пентестеров, консультантов и
изолированных команд ИБ.

**Первая цель:** локальная замена DefectDojo для одного специалиста или небольшой команды,
которым не нужен постоянный веб-сервер, но нужны findings, оценка риска, remediation и
доказуемый audit.

SOERM не пытается заменить DefectDojo как веб-платформу для крупных команд и не соревнуется с
ним числом интеграций.

## Целевой пользователь

- Пентестер или консультант, который ведёт данные клиента только на своей машине.
- Небольшая команда ИБ (1-5 человек) без инфраструктуры под веб-платформу.
- Air-gapped, регулируемые и privacy-sensitive среды, где сетевые вызовы и облачные сервисы
  недопустимы или нежелательны.

## Отличие от веб-платформ

| | Веб-платформы (DefectDojo, Faraday) | SOERM |
| --- | --- | --- |
| Развёртывание | веб-сервер, СУБД, фоновые процессы | один Python-пакет и один файл SQLite |
| Сеть | требуется | не используется |
| Интерфейс | веб, API | CLI и read-only TUI |
| Импорт | сотни форматов | ограниченный набор, каждый с тестами безопасности |
| Секреты во входных данных | - | redaction до записи в БД |
| Audit | - | hash-цепочка; подписи и якорение (M14.2) |
| Отчёты | - | детерминированные, побайтно воспроизводимые |

## Неизменные принципы

- local-first, offline, совместимость с air-gapped средами;
- SQLite, один workspace - один каталог;
- CLI для изменений, TUI только для чтения;
- fail-closed;
- redaction до записи;
- append-only audit с hash-цепочкой;
- детерминированные отчёты;
- безопасные импортёры: лимиты, без symlink, без выхода за workspace;
- approvals для решений, меняющих принятие риска;
- никаких сетевых вызовов по умолчанию; внешние данные (фиды, ключи) только из локальных
  файлов.

## Вне цели

| Не делаем | Причина |
| --- | --- |
| PostgreSQL | меняет модель развёртывания и угроз |
| Веб-сервер, API-сервер | прямое соревнование с DefectDojo, сетевая поверхность |
| Аутентификация, RBAC | требует сервера и учётной системы; заменяется подписями (M14.2) |
| Мобильный клиент | вне целевого сценария |
| Облачный режим, multi-tenancy | противоречит offline-first |
| Сетевые интеграции (Jira, Slack, email) | только экспорт в файлы |

Пересмотр этого списка - отдельное решение с обновлением модели угроз.

## Этапы M14

### M14.1 Жизненный цикл findings

Повторные сканы управляют состоянием обнаружения; решения аналитика остаются за человеком.

- Область скана (scope) и признак полного скана при импорте.
- Состояние обнаружения: присутствует / отсутствует N сканов / кандидат на закрытие.
- Политика закрытия: число чистых сканов, grace period, ручная проверка.
- Закрытие только после подтверждения; повторное открытие при возврате.
- История переходов; метрики: time to triage, time to remediation, MTTR, SLA compliance,
  reopened rate, false-positive rate.

Выход: повтор одного и того же файла не считается чистым сканом; частичный скан ничего не
закрывает; accepted_risk / false_positive не меняются автоматически; метрики видны в отчёте и
TUI.

### M14.2 Подписанная идентичность и якорение audit

- Локальный реестр ключей: добавление, отзыв, экспорт публичных ключей.
- Подпись мутаций и решений approval; запись: actor, action, timestamp, payload hash,
  previous audit hash, signature, fingerprint ключа.
- Подписанная audit head; `soerm audit verify` проверяет подписи.
- Отказ при неизвестном или отозванном ключе (fail-closed).

Выход: approval привязан к ключу, а не к тексту `--actor`; подмена БД с пересчётом цепочки
обнаруживается по подписанной head.

Открытый вопрос: проверка подписей без subprocess требует криптографической библиотеки
(новая runtime-зависимость). Порядок: Ed25519 (формат SSH-ключей), затем GPG при
необходимости.

### M14.3 Расширение импорта

Порядок: Trivy JSON, Grype JSON, Nuclei JSON, OWASP ZAP, Burp, Nessus XML, OpenVAS XML,
Snyk / Dependabot.

Для каждого: fixtures, тесты на повреждённый ввод, лимиты размера, provenance,
детерминированный mapping, тесты дедупликации. XML - только парсер без DTD и external
entities. Поля CVE / CWE и дедупликация между инструментами по CVE + asset + компоненту.

Выход: каждый формат проходит общий набор тестов безопасности импортёра.

### M14.4 Offline-обогащение

- `soerm feed import-kev FILE`, `soerm feed import-epss FILE`: только локальные файлы,
  версия и хеш фида записываются.
- Риск: CVSS + KEV + EPSS + exploit maturity + критичность актива + exposure +
  business impact; новая версия формулы (`risk-v2`), `risk-v1` остаётся воспроизводимой.

Выход: приоритет объясним по факторам, отчёт показывает версию и дату фидов.

### M14.5 Init, backup, экспорт

- `soerm init`, `soerm backup create|verify`, `soerm restore`.
- Backup: БД, метаданные audit, публичные ключи, метаданные фидов, версия схемы,
  manifest, контрольные суммы; без секретов без явного флага; безопасная распаковка.
- `soerm export csv|html|pdf`.

Выход: backup -> restore -> `audit verify` даёт ту же head; экспорт детерминирован.

Открытый вопрос: PDF без браузера и тяжёлых зависимостей.

### M14.6 Масштаб и поставка

- CI: Python 3.12 и 3.13, Linux; решение по macOS и Windows.
- Лицензия, политика публикации на PyPI.
- Воспроизводимый wheel, подписанный релиз, SBOM.
- Документация отдельно от дневника разработки (`docs/`, `CHANGELOG.md`).
- Benchmark: 50 000+ findings (импорт, пересчёт риска, отчёт, TUI).

Выход: релиз собирается и проверяется в CI; benchmark зафиксирован.

## Критерии выхода для каждого этапа

- `pytest`, `ruff check`, `ruff format --check`, `mypy` на Python 3.12 и 3.13.
- Тесты слоёв, статической политики, блокировки сети и гигиены репозитория зелёные.
- Миграции только добавляются; применённые не меняются.
- Документация обновлена; ограничения этапа описаны.
- После этапа разработка останавливается до подтверждения.

## Цель M14 достигнута, когда

Один специалист без сети может: создать workspace, импортировать результаты основных
сканеров, получить дедуплицированные findings с приоритетом на основе KEV / EPSS, вести
remediation с автоматическим закрытием и повторным открытием по повторным сканам,
подписывать решения, выпустить отчёт для клиента и восстановить workspace из проверенного
backup.

## Сохраняющиеся ограничения

- Redaction шаблонная (best-effort).
- Аргументы командной строки попадают в shell history до redaction (до ввода из
  файла / stdin).
- `flock` - advisory; workspace только на локальном диске.
- Модель угроз: один пользователь или доверенная небольшая команда на своих машинах.
